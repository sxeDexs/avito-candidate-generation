## 1. Архитектура решения

Решение построено по принципу **двухэтапного отбора кандидатов (Multi-Stage Retrieval with L1.5 Pre-ranking)**:

```
                          [Поисковый запрос + Фильтры + Геолокация]
                                               │
                                               ▼
                        ┌────────────────┬────────────────┬────────────────┐
                        ▼                ▼                ▼                ▼
                    [BM25 + TF-IDF]  [Dense E5-Base] [Dense BGE-M3]  [Smooth Geo]
                    (Лексика)        (Контекст)     (Контекст)   (scale=45km)
                        │                │                │                │
                        └────────────────┼────────────────┴────────────────┘
                                               │
                                               ▼
                    [L1: Объединение пула кандидатов Top-200 (Recall@200 ≈ 95.0%)]
                                               │
                                               ▼
                       [L1.5: Пре-ранкинг и сжатие пула (200 -> 50)]:
                  1. Exact Phrase Match (бонус за точную фразу в заголовке)
                  2. Title & Params Token Overlap (доля покрытия слов)
                  3. ParamFilt (100% совпадение чекбоксов таксономии, x1.20)
                  4. Local Shield (защита от нерелевантного иногороднего спама)
                  5. Quality Boost (разрешение споров между одинаковыми заголовками)
                                               │
                                               ▼
           [Детерминированная сортировка np.lexsort -> Финальные Топ-50 в answer.csv]
```

## 2. Данные и признаки: что использовано и почему

В ходе исследовательского анализа (EDA) были выявлены фундаментальные свойства предметной области услуг:

1. **Текстовые поля (`search_query`, `item_title_raw`, `item_description_raw`):**
   - Заголовок (`title`) является самым надежным концентратором интента исполнителя. Описания (`description`) часто зашумлены перечислением сопутствующих услуг, что сбивает лексический поиск. В связи с этим заголовок индексируется с троекратным весом.
2. **Структурированные фильтры поиска (`search_infm_params_text` vs `item_infm_params_text`):**
   - Обнаружено, что в **37% запросов теста** присутствуют жесткие фильтры-чекбоксы (*«Вид услуги Красота, здоровье»*, *«Тип услуги Ремонт авто»*). Это не свободный текст, а категориальные атрибуты. Создан модуль `ParamFilt`, сверяющий фильтры с параметрами объявлений и дающий мультипликатор $\times 1.20$ при совпадении.
3. **Геолокация и агломерации (`search_location_id`, `item_location_id`, координаты):**
   - Выявлено, что 83.1% целевых кликов совершаются в своем городе/районе, однако у 17.4% тестовых запросов в их локации нет ни одного объявления в корпусе (деление на город и пригородные районы). На основе кликов `train` восстановлены медианные центроиды локаций и реализована непрерывная функция рационального затухания по формуле Haversine ($1 / (1 + \text{dist} / 45\text{ км})$). Масштаб 45 км доказал оптимальность для объединения городов-спутников (Москва — Красногорск/Химки/Мытищи).
4. **Категориальное разделение (`search_category`, `item_category_id`):**
   - В 99.99% кликов категория запроса совпадает с категорией объявления. 100% кликов при `category == 0` приходятся на категорию Услуг (114). Реализовано подавление непрофильных товарных категорий.
5. **Отзывы (`item_rating`, `item_rating_reviews_count`):**
   - При совпадении названий в мегаполисах (например, 80 одинаковых «Услуг манипулятора» в Москве) пользователь выбирает проверенных исполнителей. Множитель `quality_boost` разрешает такие коллизии.

## 3. Модели и алгоритмы

1. **Двухбашенный плотный ансамбль (Dense Semantic Retrieval):**
   - **`deepvk/USER-bge-m3` (60%)**: 1024-мерная модель, дообученная VK специально на поисковых запросах Рунета. Превосходно улавливает сленг, сокращения (*«эбу»*, *«гбо»*, *«автоподбор»*) и нечеткие запросы.
   - **`intfloat/multilingual-e5-base` (40%)**: 768-мерная модель от Microsoft, компенсирующая длинный смысловой контекст.
2. **Векторизованный детерминированный BM25 + TF-IDF Query Expansion:**
   - По историческим кликам построен словарь расширения запросов сопутствующими терминами. Фильтрация по инверсной документной частоте исключает стоп-слова (*цена, мастер, выезд*).
3. **L1.5 Pre-ranking (Сжатие пула 200 $\to$ 50):**
   - Первый этап отбирает 200 лучших кандидатов, захватывая **~95% всех правильных ответов**.
   - Реранкер вычисляет долю покрытия токенов запроса, проверяет вхождение точной фразы, совпадение параметров чекбоксов и активирует `Local Shield` (штраф за расстояние >140 км, если в радиусе 50 км уже есть исполнители).

## 4. Проверка качества решения до отправки (Валидация)

### Проблема наивной валидации (Random Split):
Первичный случайный сплит показывал завышенный скор **~0.89**, тогда как на лидерборде было **~0.80**. Анализ выявил объективный сдвиг распределения (**Distribution Shift**):
- На случайном сплите 100% объявлений были «старыми» (из обучающего среза).
- В реальном тестовом бенчмарке **90.41% объявлений — абсолютно новые**!

### Методология честной валидации (Item-Disjoint Cold CV):
Чтобы исключить переобучение на известных объявлениях и дубликатах запросов, был построен строгий протокол валидации:
1. **Изоляция каталога (Item-Disjoint):** Все целевые объявления валидации были полностью исключены из обучающей части выборки ($Items_{val} \cap Items_{train} = \emptyset$). Никакие статистики, словари или кликовые графы не имели доступа к валидационным товарам.
2. **Группировка запросов (StratifiedGroupKFold):** Запросы валидировались строго по группам уникальных 4-компонентных ключей `(query, location, params, category)` со стратификацией по сложности.
3. **Корреляция с Leaderboard:** В рамках этого протокола валидация показала устойчивый монотонный рост: **0.8982 $\to$ 0.9025 $\to$ 0.9097 $\to$ 0.9148**. Систематическое смещение относительно LB (~0.08) обусловлено наличием в тесте 17.4% запросов из холодных локаций, однако ранговая корреляция гипотез оставалась 100% надежной.

## 5. Анализ ошибок и принятые решения

| Выявленная проблема | Живой пример из анализа ошибок | Инженерное решение |
| :--- | :--- | :--- |
| **Семантический разрыв** | Запрос *«диджей»* $\leftrightarrow$ объявление *«Ведущий DJ на праздник»* | Двухбашенный ансамбль BGE-M3 + E5 и TF-IDF Query Expansion. |
| **Отрезание агломераций** | Запрос в Москве $\leftrightarrow$ объявление в Красногорске (33 км) | Радиус непрерывного сглаживания увеличен с 25 до 45 км. |
| **Игнорирование чекбоксов** | Фильтр *«Вид услуги Красота, здоровье»* | Внедрен модуль `ParamFilt` ($\times 1.20$ за совпадение фильтра в параметрах). |
| **Насыщение мегаполисов** | 80 манипуляторов в Москве претендуют на 50 мест | В реранкинг добавлен множитель рейтингов и отзывов для разрешения споров. |
| **Ложные запреты связи** | Экстренные службы (эвакуаторы) без сообщений | Сняты любые искусственные штрафы за флаг `item_is_message_forbidden`. |

## 6. Воспроизведение решения

Решение полностью автономно, детерминировано и не обращается к внешним платным API.

### 1. Установка окружения:
```bash
pip install -r requirements.txt
```

### 2. Запуск пайплайна:
```bash
python run_pipeline.py
```
- **С кэшем (быстрый запуск, ~1 минута):**
  1. Скачайте файлы с предварительно рассчитанными эмбеддингами по ссылке: [Яндекс.Диск (cache)](https://disk.yandex.ru/d/fuGxoKjWw6BTTA).
  2. Положите файлы в предварительно созданную папку `cache/` в корне проекта.
  3. Запустите `python run_pipeline.py`. Скрипт считает готовые матрицы и выдаст итоговый `answer.csv`.
- **С нуля (без кэша):**
  При отсутствии папки `cache/` скрипт автоматически скачивает открытые веса моделей из Hugging Face Hub, самостоятельно кодирует корпус на GPU и сохраняет кэш.

### 3. Проверка формата файла:
```bash
python check_submission.py
```
Скрипт проверяет все 2 452 строки, длину каждого ID, уникальность и соответствие ТЗ.
